# Implementation roadmap and gates

1. **CPU rules reference (functional first release):** Hold'em deal, heads-up action order, short blinds, full integer-chip wager validation, preset agent sizes, all-ins, uncalled refunds, odd-chip ties, showdown, private observations, random and heuristic bots. Deterministic and seeded randomized checks pass; 5,000 independent evaluator comparisons agree. Additional exhaustive betting-tree verification remains useful.
2. **Small games (in progress):** exact Kuhn and Leduc best-response checks and synchronous CFR references now pass. NFSP improves across three seeds, but at 20,000 episodes remains 2.54–2.96 NashConv under the better tested setting. Continue stability and convergence experiments before claiming a strong small-game policy.
3. **Playable table (functional first release):** local browser game now supports complete hands against heuristic, random, and experimental Hold'em NFSP opponents, arbitrary legal integer wager targets, hidden cards, histories, and alternating button positions. NFSP uses the same engine/action abstraction it was trained on, but remains experimental and out of distribution after custom user wagers.
4. **Restricted Hold'em solving (shared postflop prototype):** `poker_cpu.solve` is the typed request/result boundary for both frontends. It returns every compatible acting-hand root strategy, conditional action EV in chips/BB, range aggregates, action gap, exact finite-game NashConv, and measured latency. `MultiStreetGame` reuses the chance-aware CFR/CFR+/DCFR updates through river, turn→river, and research-only flop→turn→river betting. One four-deal river run matched the preserved solver's frequencies, EVs, and NashConv exactly. Cached hand ranks and collapsed exact all-in runouts reduced a one-deal flop iteration from 7.47 to 2.26 seconds with unchanged EV/NashConv. A deeper exact four-deal turn reference reached 0.107-chip restricted NashConv in 16.51 seconds; faster chance-sampled CFR was more vulnerable across three seeds, so remains research-only. Flop remains disabled in the UI and preflop has no validated blueprint. Next: held-out board/range/action-EV suite, improved chance or continuation approximation that meets that suite, and a calibrated live range model.
5. **Neural continuation model (diagnosis):** the current 2.07–2.35-chip model predicts root hand-conditional EV and is not a continuation-value network. Label/payoff audits passed on sampled saved positions; suit augmentation did not improve MAE. Next: define the depth-cutoff counterfactual-value target and public-state/range encoding, then validate prediction and action regret against deeper CPU solving. Do not use the exploratory model for live advice.
6. **CPU experiment cycles:** profile search and inference, vary one factor at a time, compare fixed opponents with seat rotation and uncertainty. The 20-chip NFSP agent has been trained over three seeds; fixed-suite controls show gains against random play but losses to the heuristic. This agent evaluation is independent of browser game functionality.
7. **Solver interface and range gate:** the older `solver_interface.py` adapter now delegates to `poker_cpu.solve`; Solver Lab calls `/api/solve`, and Play & Learn constructs a live request with `request_from_game()` and calls the same API. The lab's button-opening and big-blind-defense presets remain assumptions. The range-inference module replays public board/actions with supplied hand-dependent action likelihoods, but no fitted likelihood model or held-out calibration has passed a live-use gate. Build that dataset/model and report held-out log loss, calibration, posterior sanity, and downstream action EV sensitivity before connecting automatic advice. The live table explains unsupported states street by street.
8. **CUDA only after CPU gates:** if NVIDIA hardware becomes available, benchmark PyTorch CUDA against custom C++/CUDA for profiled bottlenecks, including transfers and end-to-end game quality. Otherwise retain CPU operation and label CUDA code untested.

Each experiment should save command/config, seed, revision and dirty status, hardware, raw output, and an interpretation distinct from observation. Do not promote prior `.pt` files to benchmark evidence without provenance.
