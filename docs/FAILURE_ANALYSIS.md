# Failure analysis

## Offline training and cache limitations (2026-10-14)

The 24-hand NFSP smoke and four-hand evaluations produced real weights and losses, but the sample is far below the 100-hand minimum for automatic promotion; no stronger NFSP version was established. A 20-iteration fixed river CFR+ cache candidate had 2.09864-chip exact restricted NashConv, above the 0.1-chip cache gate, so it was rejected. These are observed gate failures, not training regressions. The 2,000-iteration demo solution measured 0.080251-chip NashConv on its own exact explicit-range game and can be sampled only for that matching situation. There is no cached preflop/flop/turn policy, no betting-history range calibration, and no neural continuation evaluator; random legal-action baseline play remains a research baseline, not a claimed cached solver opponent. The next experiment should evaluate more candidate policies with paired common-seed deals and build a tested cache-key coverage matrix before offering a cache-driven full-game opponent.

A deterministic resume regression test initially failed: stopping after eight completed hands reported nine because the loop index had advanced to the next, unplayed hand before `break`. The worker now tracks completed hands immediately after each game. The rerun passed and compared every saved seat-1 policy tensor bit-for-bit against an uninterrupted 16-hand run with the same seed/configuration. The checkpoint now also preserves curve and loss accumulators so resumed metric history remains continuous.

## E001: two failed test expectations

The first rule suite reported 5/7 passing. The conservation test added `pot` to stacks after a terminal award, double-counting chips; terminal `stacks` already include the award while `pot` remains as a hand-history amount. The short-stack test expected a three-chip flop bet although the opponent had only one chip left. Correcting the assertions made 7/7 pass. No engine defect was demonstrated by these failures.

## E002: heuristic strength unproven

In 100 hands versus random, the heuristic lost 2.68 chips/hand with standard error 5.91. This is too noisy to infer that it is weaker or stronger. It estimates showdown equity against uniformly random cards, which can misprice decisions when future betting, ranges, and fold equity matter. This is a hypothesis for future diagnosis, not a measured root cause. The current fix attempt is only to retain fixed seeds and seat rotation; no threshold tuning has been performed.

## Open validation risks

- The independent Treys cross-check found no disagreement in 5,000 seeded comparisons, but it is statistical rather than exhaustive.
- The first cross-check invocation failed with a syntax error in the new script. After fixing the missing parenthesis, the intended comparison completed with zero mismatches.
- Random games cover many transitions but do not exhaust all betting histories or inspect every unusual short all-in case.
- Historical Kuhn and Leduc scripts were preserved. Their CFR convergence and NFSP strategic quality are not inferred from saved weights or local unit checks.
- The later exploratory river model has per-hand root-value labels, but no validated depth-cutoff counterfactual-value labels or CUDA benchmarks exist.

## NFSP early plateau and incomplete convergence

At 3,000 episodes, all three η=0.1 seeds had higher exact Leduc NashConv than their untrained policies: seed 11 rose 6.51→7.19, seed 23 6.49→6.57, and seed 37 6.50→7.43. At 20,000 episodes they improved to 3.81, 3.24, and 2.98, but remained far above the synchronous CFR reference's 0.14 at 500 iterations. A 100,000-episode η=0.1 run on seed 11 reached only 2.67. Its greedy Q policy measured 5.37 NashConv, which is expected to be vulnerable in an imperfect-information game but also suggests the learned best response is still poor.

**Hypothesis tested:** too few best-response episodes and supervised examples at η=0.1 slow the average policy. We changed only η to 0.3, held the three seeds and 20,000-episode horizon fixed, and observed final NashConv 2.54, 2.96, and 2.56. The mean moved from 3.34 to 2.68. This supports a local improvement at that horizon, but three seeds and one changed setting do not establish robust optimal tuning. Other plausible contributors include fixed exploration, small memories, Adam/learning-rate choice, and the custom game's payoff scale; these are untested hypotheses.

**Gate status:** Small-game NFSP shows reproducible learning, but its policy remains substantially exploitable. A separate restricted Hold'em NFSP learner has since been trained and evaluated; the Leduc result does not establish its strength. CUDA and integration of a validated neural continuation model remain unimplemented.

## First neural river values underperformed the shallow solver

On 20 held-out public boards, the raw-card value model had 4.28 chips MAE against 200-iteration river CFR labels, worse than a zero-value predictor at 3.95. This falsified the initial hypothesis that a small raw-card MLP and 60 training boards were sufficient. Shallow 20-iteration CFR was much closer at 0.96 chips MAE.

**Root-cause hypothesis and controlled test.** River hand rank relative to the opponent's range is difficult to infer from sparse one-hot cards at this data scale. Adding one exact showdown-equity feature, with the same saved positions and labels, reduced MAE to 2.59. Adding 120 training boards while preserving the same held-out boards moved seed-53 MAE to 2.35; two other initializations gave 2.23 and 2.07. These results support the hypothesis that feature and data scarcity contribute, but do not isolate every cause. The labels themselves are approximate (reference NashConv mean 0.398).

**Decision.** Keep this network as an experimental artifact. Although its end-to-end path was about 40.5× faster than a 20-iteration solve on one tiny position, its error remains substantially larger. It is not used for live action EV or depth cutoffs. Whether it preserves strategic choices has not been tested.

### Follow-up audit: no payoff/range defect found; target does not match intended use

The historical 2.07–2.35-chip errors were MAE on 120 hand examples grouped into only 20 held-out public positions, using the same fixed split for all three network seeds. The six labels within each position share a board, ranges, and solve, so 120 is not an independent sample count. Each target is root hand-conditional EV under the average strategy of 200-iteration CFR. It is not a continuation value at a search cutoff. The 0.961-chip shallow-CFR number is the same conditional root value computed by 20-iteration CFR and compared with those 200-iteration labels; it is a direct solve of the known tiny game, not learned advice or action-regret evidence.

`experiments/diagnose_river_value.py` recomputed saved labels on four positions (maximum error 0) and checked 72 representative terminal payoff mappings against engine stack deltas under the root-pot baseline (maximum error 0). Joint deals exclude overlapping cards and normalize products of the supplied range weights. The encoded features cover the root board, private hand, explicit range hands and weights, player, pot, stack, and exact range equity; no public history is needed for this root-only target because all samples begin at the same root. No label, payoff, or range-weight implementation defect was found in this audit. A remaining limitation is that only a small sample of the saved targets was independently regenerated, and both generator and checker use the same CFR implementation.

The held-out public positions are disjoint from training boards and generated by the same sampler, but only 20 test positions support generalization claims. The full-card one-hot features expose suit identities even though suit permutations preserve poker values; a controlled four-mapping augmentation produced 2.201 MAE versus 2.134 without augmentation (RMSE 2.881 vs 2.915) on the same held-out boards. This did not improve the chosen primary metric and is not treated as a successful fix.

**Root cause of the failure to support DeepStack-style search:** the target and model input do not represent a search cutoff. They omit prior public betting history, current actor/action history, and a range-belief state at that cutoff. A model can fit a root EV target and still give invalid action values after a bet or raise. No downstream action recommendation metric was measured, so the current model has not demonstrated strategic value. The justified next step is to generate and validate actual cutoff counterfactual-value targets and report action regret against a deeper solve. The current neural river artifact remains experimental and is not a live analysis engine.

## Reward scaling gave mixed NFSP results

Dividing the DQN target reward by 20 reduced mean 20,000-episode NashConv from 2.68 to 2.49 across three paired seeds at η=0.3. One seed worsened (2.54→2.69), while two improved (2.96→2.62 and 2.56→2.16). This does not isolate reward magnitude as a consistent root cause. The default remains scale 1; the option supports later replicated tests.

## Restricted Hold'em NFSP loses chips to the heuristic

Three 10,000-hand self-play-trained average policies each played 1,000 fixed seeded hands against random and 32-sample heuristic agents. All gained chips against random (+0.86 to +1.48 per hand), and each exceeded its initialized-policy control by point estimate. All lost to the heuristic (−1.04 to −2.08 chips per hand). The initialized controls also lost to it (about −0.9), but seeds 23 and 37 got worse after training by point estimate. The trained policies still won 58.6–58.9% of all heuristic hands, so win rate alone hid the chip losses.

**Follow-up observation.** A separate 500-hand fixed-deal diagnostic for seed 11 found 191 trained-policy losses of at least 10 chips versus 148 for its initialized control. The trained policy folded 14 times versus 80, called 163 times versus 80, and raised 342 times versus 244. It went all-in less often (215 versus 286 hands), so excessive all-in frequency alone is not the explanation. Hands containing a trained-policy call averaged −9.21 chips, but that conditional result is selection-biased: calls occur in more threatening states.

**Failed fix attempt.** Replacing only faced-bet NFSP decisions with the existing 32-sample heuristic on 500 fixed deals reduced raises from 300 to 77 and increased folds from 9 to 35, but changed return from −0.708 ± 0.636 to −0.758 ± 0.553 chips/hand. Mean policy-decision latency rose from 1.05 to 5.51 ms. This narrow substitution did not support the hypothesis that a generic equity guard would repair the losses; it was not deployed to the browser. The difference is too small relative to hand variance to rank the policies confidently.

**Root-cause status.** Faced-bet decision quality remains an unproven hypothesis. Reward scaling by 20 and legal masking are already present, so neither can simply be asserted as the fix. Next, inspect range and hand-strength calibration by street or test a controlled training schedule change against the same fixed suite. No strength or equilibrium claim is supported yet.

## Longer Hold'em NFSP training did not improve the fixed suite

For seed 11, changing only the training horizon from 10,000 to 30,000 self-play hands moved the 1,000-hand fixed-suite point estimates from +1.078 to +0.817 chips/hand against random and from −1.037 to −1.505 against heuristic. The 30,000-hand checkpoint is saved separately; the playable opponent still uses the 10,000-hand policy. This one-seed result does not prove degradation, but it gives no support for the hypothesis that simply training longer resolves the current weakness. Compare multiple seeds or a targeted change to exploration, replay, or opponent diversity before selecting a new default.

## E026: playable engine and browser edge-case failures

The first regression assertions for odd-chip ties and short-blind conservation were wrong: the tie test left the constructor's 100-chip initial-stack baseline while replacing its stacks with 10-chip values, and the short-blind test added the displayed terminal pot to stacks after that pot had already been awarded. The tests were corrected to use consistent initial stacks and to distinguish in-progress chip conservation (`stacks + pot`) from terminal conservation (`stacks`). The engine's tie payout and short-blind refund then passed.

A table test that expected showdown used a random opponent and could terminate by fold. It now uses a passive deterministic test agent. During that regression, terminal-card privacy exposed a real bug: `winner is None` means a tied showdown as well as the initial/no-winner state, so it cannot distinguish folds from showdowns. Added `game.showdown`, which is set only by `_showdown`; the browser now reveals opponent cards for wins and ties at showdown and keeps them hidden after folds. The 43-test suite passed after the fix.

The first end-to-end HTTP smoke attempt failed an assertion in its completion checks. A traced rerun verified the returned action history and showed the heuristic can terminate a hand through fold as well as showdown; the final smoke used a complete legal action loop and passed through showdown and the alternating next hand. The initial assertion did not isolate an additional product defect. The showdown-vs-fold disclosure bug described above was an application defect and is fixed.

The underlying engine limitation that preset actions were also treated as the complete legal action set is resolved: arbitrary integer targets are checked against minimum full raise, effective stack, and raise-reopening rules. Short stacks below the big blind and odd-chip ties are now covered. Still open: carry-over bankroll semantics, tournament elimination, and multiway side pots are outside the current heads-up per-hand trainer.

## E027: river action-value and update-rule validation

The first new report tests failed before any benchmark result was accepted: the conditional-EV report referenced an unbound deal-weight variable, and the adapter test fixture gave `RiverGame` preconstructed `WeightedRange` objects instead of the documented hands/weights inputs. Both were interface/test construction errors, corrected and rerun. The full 50-test suite then passed.

An early draft of the CFR-variant benchmark timed cumulative wall time around `analyze_root()`, which also computes exact NashConv. That overstated training time. The script was changed to time only `solver.train()` and record action/NashConv analysis separately; the reported timings use the corrected script and raw JSON. Repeated CPU timings still varied (the 2,000-iteration CFR+ run was about 11.6 seconds in the recorded run), so the single run is not treated as a systems speed result.

The observed convergence check is promising but narrow: on one fixed nine-deal game, 2,000-iteration CFR+ and DCFR had exact abstract-game NashConv 0.0184 and 0.0200 chips; vanilla CFR was 0.1385. All three values are nonzero. A lower NashConv on this one tiny game does not validate a full-range river strategy, UI feedback, or DeepStack-style solving. The exact best-response evaluator shares the same game transitions and terminal payoff definitions as CFR, although conditional action EVs were separately checked by a brute-force traversal. A future independent validation should use a second implementation or a known solved abstract poker game and compare across multiple independently sampled boards/ranges.

The strategy-frequency and action-EV API was at risk of returning an aggregate range EV gap as the acting player's actual EV loss. That is wrong for a specific observed hand. It now reports `chosen_action_ev_loss` only when the acting private hand is supplied; otherwise it leaves that value absent and labels any range-level comparison as `range_average_action_gap`. This local gap still holds the continuation policy fixed, so it is not a full strategic exploitability measure.

## E028: convergence varies by sampled river position

The five-position seed-729 suite completed without a transition or range-validation failure, but 500-iteration CFR+ NashConv ranged from 0.0056 to 0.2038 chips. This is a measured spread, not evidence of uniform convergence. Positions with higher residual NashConv need more iterations or a different abstraction/update; no shared iteration count can be presented as a global quality threshold based on this sample. The ranges were deliberately constructed from mutually disjoint cards across both seats, so this run does not test the harder overlap/blocker posterior cases beyond the separate unit tests.

## E029: initial DCFR update order was incorrect

Reviewing the first DCFR implementation showed that it discounted cumulative regrets after computing the iteration's regret-matching strategy. DCFR must form that strategy from the discounted regrets, so the initial update did not implement the intended recurrence and its first benchmark row was not accepted. The discount operations now run before traversal; the current iteration's regret increments are added afterward, and the existing average strategy is discounted before new contributions. The full 50-test suite and the 20/100/500/1,000/2,000 comparison were rerun. Corrected DCFR NashConv at those checkpoints is 1.7983/0.4505/0.1036/0.0509/0.0200 chips. It remains an implementation of the stated DCFR discount equations in a synchronous tiny tree, not a reproduction of every variant or optimization from the paper.

## E031: a short computation budget does not produce converged advice

On the recorded 10 ms adapter request, one atomic CFR+ iteration overshot the search budget slightly and the solver stopped after three iterations. Exact best-response NashConv was still 5.432 chips, while end-to-end latency was 20.11 ms after the additional diagnostics. The returned action frequencies and action EVs are mathematically defined for the approximate profile, but this profile is highly exploitable and should not be presented as GTO-like feedback. The adapter marks only that the implementation is tested and returns the residual diagnostic; the live UI does not consume these fields. The raw result is `experiments/river_adapter_budget.json`.

## E032: River Analysis panel validation and remaining quality limits

The first new test run found assertion wording mismatches: the server correctly returned lowercase `exact NashConv` and described the supported root as having “no prior river actions,” while the tests expected capitalization and “first river decision.” After moving zero-compatible-hand validation before CFR training, one test also needed its expected error updated to the more specific message. These were test expectation defects; they were corrected. The final full run passed 53/53. Invalid board length, hero hand omitted from the hero range, zero hero-hand weight, and an iteration budget below 20 are explicitly rejected. The local HTTP smoke returned a valid analysis response.

The feature's output is correctly scoped but not yet high-quality advice by a demonstrated threshold. On its saved 500-iteration sample, exact restricted-game NashConv fell from 0.82848 to 0.48939 chips at the halfway/final checkpoints, remaining nonzero. This one hand/range fixture does not establish general convergence. Action EV loss is a root one-action comparison for the entered hero hand while future actions follow the solver's average strategy; it is not a full deviation value or live-hand regret. The manual ranges can be inconsistent with the actual action history because the panel has no range-inference model. The app states this directly. Range normalization review found an unhandled overflow case where individually finite weights summed to infinity and normalized to zero; `WeightedRange` now rejects non-finite totals, and a regression test covers it. Prior river actions, turn/flop positions, richer action abstractions, and neural continuation values remain unsupported and must continue to show as unavailable rather than inherit river outputs.

## E033: range provenance and street-specific solver limits

The new button-opening and big-blind-defense presets are illustrative 100 BB class frequencies, not learned action models or solved charts. They expand to 666 and 822 suit combos respectively, much larger than the current eight-combo river solver limit. The UI shows the count, blocks a solve that exceeds the limit, and lets users clear/narrow a range. The default small river examples are also assumptions. No result from these presets should be described as an inferred opponent range.

Bayesian range updating now replays public board/actions and requires a hand-specific action-likelihood callback. The arithmetic and impossible-observation behavior have tests, but no fitted/calibrated likelihood provider has been evaluated on held-out actions. This is the main gate for automatic live analysis. The game continues to show a street-specific unavailable explanation rather than using arbitrary likelihoods or unvalidated ranges. Preflop/flop/turn CFR betting-tree traversal is also missing; the new public-card transition module covers only chance probabilities and blocker conditioning.

At one later river state (hero check, opponent bet-to-10), 500-iteration exact restricted NashConv was 0.850238 chips and fell to 0.111001 by 2,000 iterations. The post-action ranges in this benchmark were deliberately not action-conditioned, so the reduced residual is only solver convergence in that supplied finite game. It cannot validate advice for the actual betting history. A separate opponent-check root and terminal call/fold payoff test passed, but broader action-tree and range-model validation remain. During the HTTP smoke, a test assertion incorrectly expected the served JavaScript source to contain its filename; the server returned 200 and the corrected check of the exported editor passed. No product defect was inferred from that failed smoke assertion.

## One-street flop/turn approximation cannot supply full-street advice

The new exact-runout flop/turn reference produces finite-game CFR+ frequencies and conditional action EVs, including after a current-street bet. It assumes no later betting once the current street closes. That assumption omits future value betting, bluffing, and range updates, so even a low one-street NashConv does not measure exploitability in the full multi-street game. In the measured two-combo-per-seat fixture, 200 iterations yielded NashConv 0.08849 chips on turn and 0.06864 on flop; flop equity enumeration alone took 1,535.41 ms in the saved rerun. These are functioning reference results, not a failed test, but they fail the full-street advice requirement. The model stays out of the trainer UI. Next test: add a tiny explicit turn continuation after flop, compare per-action values with the one-street approximation, and record both decision regret and runtime before extending the state space.

## Exact flop-to-river traversal fails current interactive quality gate

Adding true public chance and future betting to the shared CFR tree fixed the one-street continuation omission for tiny postflop games. It also exposed tree cost: one private deal, 1-chip effective stacks, no raises, and just **one** exact flop CFR+ iteration took **8,766.32 ms** and left **2.426894 chips** of exact restricted-game NashConv. This result is too slow and far from convergence for trainer advice, so the UI explicitly disables flop analysis. The research API requires an experimental flag and enforces a one-deal, three-iteration cap. The measured cause is the 45 possible turn cards followed by 44 river cards per private deal, each with future betting branches; a profiler and scaling study are still needed to attribute time precisely among traversal, evaluator, and Python object overhead. Next, compare statistically checked chance sampling or a validated continuation evaluator against exact tiny-game root EVs and action regret.

## Unified API does not yet imply live strategic validity

Play & Learn now constructs a typed request from the actual engine's public board, action history, pot, stacks, and visible hero hand, and calls the same solver API as Solver Lab. That request correctly returns `unsupported`: a calibrated initial-range/action-likelihood pipeline is still missing. Sending manually assumed or uniform ranges as if they were inferred would turn precise finite-game NashConv into misleading live advice. The UI keeps the unsupported explanation and the lab requires explicit range assumptions. The next validation needs held-out likelihood calibration by street/action size, posterior coverage of known hands, and root action-EV sensitivity to range error; arbitrary real-game wager sizes outside the solver abstraction also need replay support.

## NashConv target can remain unmet and checkpoints are not monotonic

The optional Solver Lab stopping target is measured using exact finite-game best responses. On the saved three-combo river fixture with a 40-iteration cap, targets of 0.25 and 0.05 chips were not met; final NashConv was 4.314712 chips. Checkpoints varied from 10.003315 at iteration 20 down to 5.729797 at 28, then up to 6.341446 at 36 before reaching 4.314712 at 40. This is actual evidence that the measured residual need not decrease monotonically each checkpoint. A loose target of 1,000,000 chips was met at iteration 20, validating early-stop plumbing only. The UI reports the actual target status and trace and describes the scope as the supplied finite game. Best-response checkpoints also increase end-to-end time, especially on larger ranges. A future cadence change needs measured runtime/decision-quality comparisons; do not smooth values or infer a stronger convergence guarantee.

## E037: chance sampling reduces runtime but fails the quality comparison

The first sampled-CFR run raised `ZeroDivisionError` during exact best-response analysis. A sampled information set had been visited only with zero own reach, so its cumulative average-strategy weights summed to zero. The fix makes `average()` fall back to a uniform legal policy when that total is zero; the deterministic seeded and 500-seed mean-regret tests pass. Such a fallback still signals sparse coverage, not a reliable strategy at that information set.

In the fixed-position experiment, 1,000 sampled vanilla CFR iterations gave 0.529–0.534 chips restricted NashConv on the one-deal flop and 0.659–0.754 chips on the four-deal turn. Exact CFR+ references gave 0.102 and 0.107 chips respectively, though they used 20 and 300 iterations and different update rules. Sampled runs were faster, but final exact best-response and action-EV comparisons did not support enabling them for advice. More seeds, variance reduction, better coverage, and held-out positions are needed. The research API labels sampled results experimental; Solver Lab and Play & Learn do not request them.

## E037: class-level state caches retained completed games

The `MultiStreetGame` legal/advance/chance/payoff methods used `lru_cache` decorators on instance methods. Those class-level wrappers keyed by `self` can retain finished game objects, and `maxsize=None` on two methods gave no bound. Replaced them with bounded per-game wrappers. A weak-reference regression test creates a game, uses its caches, drops references, runs collection, and confirms the game is released. Peak process memory across realistic ranges remains unmeasured; this fix addresses a concrete retention path, not the full scaling problem.

## E038: small modal-action loss does not validate broad turn advice

On three fixed four-deal turn boards, the largest loss from the 100-iteration profile's most frequent action, scored under a 300-iteration profile, was 0.040842 chips. Yet one conditional action EV differed by 0.234463 chips and the 100-iteration solves took 5.5–5.8 seconds. Both profiles use the same narrow range and no-raise abstraction; the deeper profile is not an equilibrium oracle. The apparent modal-action agreement may fail under other ranges, bet sizes, and earlier action-conditioned beliefs. The UI therefore retains manual turn analysis with visible residual and does not attach it automatically to gameplay.

## E039: first Chrome demo check had a test assertion error

The first end-to-end browser run reached the real solver response, action rows, selected-action EV feedback, and range grid, then failed because the test expected the strategy heading's `innerText` to contain title-case `Bet to`. CSS capitalized the displayed heading. The assertion was changed to inspect text case-insensitively; the complete rerun passed. There was no measured solver or product failure from this assertion. The passing browser run confirmed that changing actions did not make another solver request and that the normal game could start after leaving the demo.

## E040: experimental review has no calibrated opponent posterior

The saved-hand review can replay a real public river decision through the shared solver, but its opponent range is three fixed illustrative combinations after card removal. It does not condition on prior check/call/bet actions or match the selected opponent model. Consequently, the seeded run's 0.00007175-chip NashConv certifies only the tiny game built from those assumptions. It cannot be used to claim the player's real check had zero full-game EV loss or that the opponent would hold those hands with those weights. The UI labels the source, displays the exact opponent combos, and requires a user click; default gameplay feedback remains unavailable. The next test requires a separately evaluated action-likelihood model and held-out posterior/range sensitivity metrics.

During verification, the Chrome test's Node `fetch()` startup polling failed with an `undici` parser assertion before loading the app. Replacing only that polling step with `node:http` eliminated the failure in the next isolated browser run. The Python suite remained green throughout. A later deterministic browser fixture played a complete real hand, clicked the river review, and verified the rendered values against its HTTP response. This validates the UI/server wiring but still does not test range accuracy against real opponents.

## E042: default live feedback fails before CFR; full turn traversal is too slow

The seeded full-hand trace in [LIVE_SOLVER_DIAGNOSIS.md](LIVE_SOLVER_DIAGNOSIS.md) found distinct blockers. `request_from_game()` correctly captures the public state but deliberately leaves `ranges=None`; `solve()` returns unsupported for every postflop default live request. Preflop is rejected even earlier because no preflop tree exists. Supplying illustrative ranges made the three-deal flop fail the exact-tree cap. A three-deal, 98-chip-stack turn solve took 13.45 seconds for **one iteration** and had 43.5924-chip restricted NashConv, so showing its values would be misleading. These are actual code-path and latency failures, not a generic “not validated” label.

Routing flop and turn through the preserved one-street exact-runout game fixed the missing API/UI path and reduced this fixture to 1.53 seconds and 0.47 seconds for 500 iterations. This changes the modeled game: there is **no betting after the analyzed street**. Its low finite-game NashConv cannot establish full-game action-EV accuracy. The UI labels this limitation and makes review opt-in. The fixed illustrative opponent range is blocker-compatible but not action-conditioned; range error is still unmeasured. Preflop remains unsupported. The diagnostic adapter's first run raised `AttributeError` on a `RiverState.chance` lookup; using `getattr` fixed it and the independent-reference adapter test passed.
